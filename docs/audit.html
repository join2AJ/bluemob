BlueMob Engineering Audit

A senior full-stack review of the offline mesh app: what's solid, what was risky, what I fixed in 0.5, and what to build next so BlueMob holds up when someone's life depends on it.

The short version

The product idea and the delivery engine are strong. Messages have unique IDs, are stored before sending, are deduplicated on arrival and have real receipts. That is the hard part, and it's done well. The weak spots were the ones every first version of a mesh app has. Anyone could claim to be anyone. Nothing worked with the screen off. Messages only reached people in direct range.

All three are fixed in 0.5. You can now message anyone by their BlueMob ID, even someone you've never met. The message travels phone to phone, end-to-end encrypted. The biggest remaining risks are real-world ones: battery drain, behaviour on many different phone models, and no crash reporting yet. The next step is a field test with real phones, not more features.

How "message by ID" works

Asha types Kabir's ID. They've never met and are kilometres apart. Ravi walks between their groups.

  • Key lookup. Asha's phone needs Kabir's public key to encrypt. It asks phones nearby. Anyone who knows the key can answer, and the answer proves itself because the key must hash to Kabir's ID.
  • Spray and wait. A message starts with 8 copies. Each hand-off gives away half; the last copy is kept for Kabir himself. That reaches people quickly without flooding.
  • Receipts clean up. Kabir's delivery receipt travels back the same way. Every carrier that sees it drops its copy of the message.
  • Honest timing. Delivery depends on people moving between groups. It can take minutes or hours, and messages expire after 3 days. The ticks always show the truth.

Open findings and roadmap

Nothing below is broken today. These are the gaps between a working app and a service people can rely on in an emergency.

Now · next 2 to 4 weeks

O1
Field test with 5 to 10 real phonesCritical

Emulators can't use Bluetooth with each other, so the mesh has only been tested with simulated phones. Measure time to first connection, link stability while walking, delivery rate over 1, 2 and 3 hops, and battery per hour across at least three phone brands. Add a "Diagnostics" export (log plus counters) to make this easy.

O2
Battery duty cyclingHigh

Advertising and scanning nonstop is the biggest battery cost. Add a low-power mode: scan for 20 seconds every 2 minutes when no one is around, stop scanning when enough phones are connected, and switch to it automatically under Battery Saver. An active SOS always overrides it.

O3
Crash and freeze reportingHigh

There is none today, so failures in the field are invisible. Add opt-in crash reporting (Crashlytics or Sentry). Queue reports on the phone until it has internet.

O4
SOS spam controlsMedium

Partly addressed in 0.6: an SOS alert now shows the sender's stars and any fake-SOS reports. Still to do: per-sender rate limits, "Mute this sender" on the alert, and a block list.

O18
Ratings tied to real meetingsMedium

Make a rating count fully only if the rater can prove they met the person: a signed proof exchanged when two phones connect, or membership in the rescue group. That makes ratings from fake identities worthless.

O5
Late joiners can't see a rescue groupMedium

A phone that never heard the SOS itself hides its group. Phones should re-share an active SOS (still signed by the person in need) with anyone who connects, for a few hours. Also store other people's signed group messages, so they can be passed on after a restart.

O6
Forward secrecyMedium

Each pair of phones uses one fixed encryption key. If a phone's private key is ever stolen, messages captured earlier could be read. Move 1:1 chats to the Signal protocol (prekeys plus Double Ratchet, for example libsignal).

O7
Room schema export and migration testsMedium

Turn on exportSchema, commit the schemas, and add MigrationTestHelper tests on a device, so no update can ever wipe someone's messages.

Next · 1 to 3 months

O8
Deploy and scale the relayHigh

Built in 0.6 (server/relay.js). Next: deploy it with HTTPS, move storage from the file to Postgres or Firestore as traffic grows, add monitoring, and handle the SMS gateway for loved ones.

O9
Background reliability across brandsHigh

Xiaomi, Oppo, Vivo, Realme and Samsung kill background apps aggressively. Add per-brand setup guides (auto-start, battery exceptions) inside Connections, and check the foreground service on each brand during O1.

O10
LanguagesMedium

All text is hard-coded in English. Move strings into resources and add Hindi first, then regional languages. The survival guide content needs a professional medical translation and review, not machine translation.

O11
AccessibilityMedium

Add TalkBack descriptions to the radar, compass and trail map. Check layouts at 200% font size. Add a hardware SOS shortcut (for example, press power five times) for when the screen can't be used.

O12
Offline mapsMedium

MapLibre with vector tiles downloaded per region before a trip. Draw the trail, base camp and the people coming to help on the map.

O13
Trip groups and voice notesLow

Group chats beyond rescue groups, using sender keys. Short Opus voice clips, which fit the mesh. Live calls only over Wi-Fi links.

O14
Code structureLow

The ViewModel and root screen have grown large. Split them per feature, move routes to type-safe Navigation Compose, and add dependency injection (Hilt) once a second developer joins.

O15
Mesh simulator in CILow

Grow the router test harness into a 50-phone simulation with movement, so routing changes are judged by delivery rate and copies per message before they ship.

Later

O16

Bridges to LoRa radios (Meshtastic) for text over several kilometres, satellite SOS on phones that support it, and a Wear OS panic button.

O17

Backend plan for the internet bridge

When any phone in the mesh has internet, it uploads carried messages to the relay and downloads messages waiting for people nearby. The rules that matter:

  • No accounts, same keys. Every request is signed by the phone's device key. The server checks the ID-to-key hash exactly like phones do.
  • Ciphertext only. The server stores the same encrypted packets the mesh carries. It can't read messages, and a breach exposes no content.
  • Same dedup, same receipts. Messages are stored once by message ID. The first delivery wins, whether by mesh or internet, and receipts cancel the other path. The app already models this.
  • Stack. Firebase works for a pilot: Cloud Functions to check signatures, Firestore with expiry rules, FCM to wake recipients. Move to a small Kotlin or Go service on Cloud Run with Postgres if costs or control demand it.
  • SMS to loved ones. Use an Indian SMS gateway (MSG91 or Gupshup) with DLT-registered templates. Limit how many texts each phone and each number can trigger, and confirm a number before it's used for anything other than SOS.
  • Privacy law. India's DPDP Act 2023 applies. Ask for clear consent for SOS contacts and location, collect only what's needed, delete on request, and keep data in an Indian region.

Limits to know

Everything in 0.5 is tested with simulated phones, not yet between real phones. All phones must update to 0.5: it uses a new, signed protocol and won't link with 0.4. Each phone's BlueMob ID changes once to the new key-based ID, and chats with old IDs won't continue. Delivery to people out of range depends on people moving between groups, so it is not instant and not guaranteed. A rooted phone can still read its own stored data.
